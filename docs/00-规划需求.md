# juice-cli 增强规划需求（方案基线）

> 📌 **状态：规划中（2026-09-22 起）**。本文是**需求/方案基线**，提交后**不回改**；实际落地与差异见 `09-复盘.md`（待建）。
> 文档价值在于「与代码一致」——下文所有「现状」均由代码取真值，非凭印象。

## 0. 背景与目标

`juice-email-cli` 当前基于 **juice（CSS 内联）+ Mustache（模板）+ html-minifier（压缩）** 生成邮件 HTML，支持右键菜单、片段组装、变量替换、列表循环。

用户希望增强开发体验，提出 4 项需求：

1. **保持现有右键交互模式**
2. **支持引入外部 CSS（如 Bootstrap、UnoCSS）**
3. **支持片段引入**：页面由多个板块组成，各板块独立维护，按需逐个引入组装，**最好可传参**
4. **循环渲染支持索引 + 必要的逻辑判断**

本文目标：先用代码证伪现状，再列候选方案与决策点，供逐项核验，不擅自实现。

## 3. 缺口、约束与冲突

- **缺口**：③、④ 两项当前完全不支持。
- **硬约束 1（邮件客户端）**：不加载外链 CSS；弱/不支持 `flex`/`grid`/`rem`/`:hover`/复杂后代选择器。→ 直接否定「Bootstrap CDN 引入」与「Bootstrap 直接内联」的可用性（即使机械内联，产出也破版且 ~150KB 死代码）。
- **硬约束 2（引擎）**：Mustache 无逻辑 → 需求④必须「扩展引擎」或「渲染前预注入索引」。
- **命名空间冲突风险**：若③用无参 partials，多个板块若用同名变量会互相污染，需靠命名空间隔离。

### 邮件客户端 CSS 支持矩阵（供核验②选型）

| 特性 | 邮件客户端支持 | 备注 |
|---|---|---|
| 内联 `style=""` | ✅ 全支持 | juice 产出形态 |
| `<style>` 类选择器 | ⚠️ 部分 | Gmail/Apple 支持；Outlook(Word 引擎) 多半不支持，必须内联 |
| `@media` 媒体查询 | ⚠️ 部分 | 移动端支持，Outlook 不支持 |
| `:hover`/`:active` | ❌ 多数不支持 | 已被 `preservedSelectors` 保留，但实际无效 |
| `flexbox`/`grid` | ❌ 基本不支持 | Bootstrap 响应式核心全废 |
| `rem`/`vw` 单位 | ❌ 不支持 | Bootstrap 大量使用 |
| 外链 `<link href=cdn>` | ❌ 被剥离 | 物理不可行 |
| 间距/字体/颜色/基础 `display`/`width` | ✅ 支持 | UnoCSS 安全区 |

## 4. 候选方案对比

### 4.1 需求② 外部 CSS（Bootstrap / UnoCSS）

| 方案 | 说明 | 工作量 | 风险 | 评价 |
|---|---|---|---|---|
| B0 手写 `<style>`（现状） | 模板内手写，最稳、邮件安全 | 零 | 低 | 开发慢、复用差 |
| B1 本地 CSS via `extraCssFiles` | 配 `juice.extraCssFiles:[vendor.css]`，本地文件内联 | 零（机制已支持） | 低 | 适合引入已确认邮件安全的第三方 CSS |
| B2 Bootstrap 直接引入 | 借 B1 机制内联本地 Bootstrap | 零代码 | **高** | **不推荐**：flex/grid/rem/选择器在邮件不可用，必破版 |
| **B3 UnoCSS 生成静态 CSS（推荐）** | 从模板提取用到的原子类 → `uno.css` → 内联 | — | 中 | 输出精简、仅含用到的类 |
| ├ B3a 用户自生成 | 本地跑 `@unocss/cli` 出 `uno.css` 再走 B1 | 零代码 | 低 | 多一步人工 |
| └ B3b 工具内置预步骤 | 流程内自动扫 class → 调 UnoCSS 运行时出 CSS → 内联 | 中 | 中 | 需加 `unocss` 依赖 + 自定义 email-safe preset |
| B4 邮件框架 CSS | Foundation for Emails / MJML 产出 CSS | 中 | 低 | Bootstrap 的邮件安全替代 |

### 4.2 需求③ 片段引入带参

| 方案 | 说明 | 工作量 | 风险 | 评价 |
|---|---|---|---|---|
| C0 现状 | 单 snippet 插入 `content` | — | — | 无参 |
| C1 Mustache partials `{{> name}}` | 引擎原生；工具传 `partials` map | 小 | 中 | partial 不能传参，靠命名空间变量；多板块易污染 |
| **C2 YAML 页面编排器（推荐）** | page 配置列板块顺序 + 每块独立 `vars` 子树，工具顺序拼 `content` 各自渲染 | 中 | 低 | 天然传参、不互相污染；新增 `juice build -p page.yaml` 模式 |
| C3 自定义 include 指令 `{{< section }}` | 工具预解析替换，可带 inline 参数 | 中高 | 中 | 灵活，但自写解析器、与 Mustache 混用易乱 |
| C4 Handlebars partials 带参 | 若④选 Handlebars，`{{> section data}}` 传独立 context | 取决于④ | 低 | C2 的引擎原生版，最自然 |

### 4.3 需求④ 循环索引 + 逻辑判断

| 方案 | 说明 | 工作量 | 风险 | 评价 |
|---|---|---|---|---|
| D0 现状 | `{{#list}}` 无索引无逻辑 | — | — | 不满足 |
| D1 索引注入 transform | 渲染前给数组项注入 `index/isFirst/isLast/isOdd` | 小 | 低 | 仅解决索引，**无真正 if 逻辑** |
| **D2 换 Handlebars（推荐）** | Mustache 超集，现有模板几乎无缝；原生 `@index/@first/@last` + `{{#if}}` + 自定义 helper | 中 | 中（回归面） | 一次解决索引 + 逻辑 |
| D3 Nunjucks / Eta | `loop.index`、`if/else`、macro 传参 | 大 | 高 | 偏离大、模板不兼容 |
| D4 Mustache lambda 模拟 | section lambda 拼条件 | 中 | 高 | 写法丑、难维护，不推荐 |

**D2 迁移注意点（需核验）**：现有 `rawHtml`（变量内 HTML 不转义）在 Handlebars 对应 triple stash `{{{var}}}` 或 helper，须写映射保证现有模板行为不变；现有 edm 模板数量 = 回归面。

## 6. 需你核验 / 决策的清单（力度选择）

请逐项确认，我再出分步实施计划：

1. **④到底要不要「真逻辑」**：只要索引/首尾/奇偶 → D1 够；要 `if`/比较/分支 → 必须 D2。
2. **现有 Mustache 模板数量**：决定换 Handlebars 的回归成本（当前可见 elabscience/procell 各一套模板 + 若干 snippet，是否还有未提交的？）。
3. **UnoCSS 内置（B3b）还是先用 B3a 手动**：B3b 需加 `unocss` 依赖——你此前要求「安装由你执行、优先不新增依赖」，需权衡。
4. **③编排器入口形态**：新子命令 `juice build -p page.yaml` 还是扩展现有交互流程。
5. **右键菜单是否加「页面装配」入口**（仅 Z 需要）。

## 7. 增量实施与提交计划（若采纳）

遵循你「大任务按小节增量提交」的习惯，**新增模式与现有 `-s`/`-f`/交互并存，不破坏**：

- **小节 1**：引擎决策落地 —— D1 索引注入 或 D2 换 Handlebars（含 `rawHtml` 映射 + 单测）
- **小节 2**：YAML 页面编排器（C2）—— 新增 `juice build -p page.yaml`，复用 `insertIntoContent` 做多板块拼装
- **小节 3**：UnoCSS 集成 —— B3a 文档化 或 B3b 内置预步骤 + email-safe preset
- **小节 4**：（可选）右键菜单加「页面装配」入口
- 每节：**写 → 跑 `npm run lint` / `vitest` / `smoke` → 独立 commit + push**

## 8. 已知限制与风险

- Handlebars 迁移回归面：需先清点全部 edm 模板（决策点 2）。
- `rawHtml` 在 Handlebars 下须映射为 `{{{ }}}`，否则变量内 `<sup>` 等会被转义。
- UnoCSS 预设须自定义为 email-safe（屏蔽 grid/transform/flex 等），否则内联后破版。
- 依赖取舍：B3b 与「不新增依赖」偏好冲突，需你拍板（决策点 3）。
